# Update Dependencies

Use this skill for dependency update work in Gradle projects. Match the scope in the request: report available versions when asked to check; edit version pins when asked to update. Do not infer permission to commit from a request to update.

In BESTV, `gradle/libs.versions.toml` is the central version source and Dependabot handles scheduled update PRs. BESTV does not provide a local dependency report task; use official release information for on-demand checks.

## Workflow

1. Inspect repository instructions, the working tree, Gradle build files, and the version catalog. The version catalog is the required source of truth for external dependency and plugin coordinates and versions; if it is missing or pins are stored elsewhere, migrate them into the catalog. Preserve unrelated user changes and avoid replacing an already modified file wholesale.
2. Use a dependency report task only when the project already provides one; do not add a reporting plugin solely for this skill. For BESTV, use the Dependabot configuration as scheduled automation, but perform manual checks by comparing pinned versions in the catalog and root build classpaths with official release sources. In other projects, run their existing dependency report task and inspect all relevant modules. Check buildscript plugin coordinates against their official release source or plugin portal because project dependency reports may omit them.
3. Select stable releases only. Treat suffixes such as `alpha`, `beta`, `rc`, `milestone`, `preview`, `snapshot`, and `canary` as prereleases. A report section called “later milestone versions” can contain both stable and prerelease candidates, so classify each candidate by its version. A stable release can replace a currently pinned prerelease when the report offers it.
4. Update only dependencies within the requested scope and with an explicit pinned version in the project. Put coordinates and version pins in the version catalog, and update every occurrence that must stay aligned, such as OkHttp and its logging interceptor or dependencies managed by one BOM. Do not add direct pins for transitive-only dependencies unless they are needed to fix a demonstrated compatibility issue, such as an annotation processor that cannot read the Kotlin compiler's metadata version.
5. Leave prerelease candidates out unless the user asks for them. For buildscript classpath updates, check compatibility among related Android Gradle Plugin, Kotlin, Compose compiler, and Gradle versions before changing pins. Do not change the Gradle wrapper unless the user includes it in scope. When the wrapper is in scope, check the wrapper version against the official compatibility ranges for the selected Android Gradle Plugin and Kotlin Gradle Plugin, then choose a stable version supported by both where possible. Include other build-time processors that consume Kotlin metadata (for example, Room's KAPT processor) in the compatibility check; a version-matrix match alone is not enough if the project build demonstrates processor incompatibility. If no compatible stable set can be verified, keep the conflicting pins unchanged and explain the blocker rather than knowingly leaving the build broken.
6. Review the diff and working tree. Keep changes limited to requested dependency declarations, version catalogs, and (when explicitly in scope) wrapper files; preserve unrelated edits. After applying updates, verify dependency resolution and compilation separately. For Android, run the app's main runtime dependency report when available (for example, `./gradlew :app:dependencies --configuration debugRuntimeClasspath`) and then build the app (for example, `./gradlew assembleDebug`). When changing annotation processors or Kotlin versions, also inspect the relevant processor configuration (for example, `./gradlew :data_shared:dependencyInsight --configuration kapt --dependency kotlin-metadata-jvm`). Use equivalent resolvable configurations and build tasks for other Gradle projects. Consider verification successful only when dependency resolution and the build pass. If either fails, inspect the first relevant failure, make an in-scope compatible adjustment or revert only the incompatible update, then rerun both checks. For IDE sync errors such as a corrupt serialized resolution result, reproduce with the corresponding CLI dependency report and check Gradle/dependency-resolution compatibility before treating it as a local cache problem. Report exact tasks and outcomes; do not run tests unless the user asks for them.
7. If the user explicitly asks for a commit, stage only the dependency files changed for this task, inspect the staged file list and diff, then commit. Never include unrelated staged or unstaged work.

## Reporting

State which reports or official sources were checked, list the meaningful stable version changes, identify prerelease candidates excluded when useful, and say whether verification was run. For a check-only request, do not change files.
